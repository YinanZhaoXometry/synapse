1. **Operation set mirrors the repo exactly.** task-repository: `createStudyTask` → `createTask`; `getTask` → `task(id:)`; `listTasks` → `tasks`; `getTaskNode` → the `StudyTaskType.node` association. material-repository: `registerMaterial` → `attachMaterial`; `getMaterial` → `material(id:)`; `listMaterials` → `materials` (no args); `listMaterialsByPlan` → `materials(planId:)` **and** the `StudyPlan.materials` association; `listMaterialsByTask` → `materials(taskId:)`; `setMaterialParseResult` → `setMaterialParseResult`.
2. **No task delete/update, no material detach** — Phase-1's repositories expose none (diff), so none land. `markMaterialParsing` is the one repo op deliberately not mirrored: the eager-parse-at-attach flow (AD-7) attaches with `parseState: "parsing"` directly (attach accepts the full ParseState vocabulary), so the only post-attach transition with domain weight is the final outcome write-back, which lands. A separate pending|failed→parsing op would be a UI-transient no-op server-side.
3. **Idempotency keys are new server-side contract** (delta 3): Phase-1 mints uuids client-side with no replay concept. Task and material carries take `clientUuid` (named to avoid Relay's `clientMutationId` confusion, ticket-01 convention): same-user replay → Success returning the existing rows untouched (the replay payload is NOT re-applied — re-upload safe); the uuid owned by a different user → VALIDATION_FAILED; non-uuid → VALIDATION_FAILED. `RecordNotUnique` race backstops re-decide via scoped re-lookup (the `Plans::PlanCreation` template).
4. **The 100,000-char section cap replaces Phase-1's silent truncation** (kickoff delta 6): the client repo `boundText`s at 2,000 chars/section; the server REFUSES beyond 100,000 with VALIDATION_FAILED — silently rewriting the client's extracted text is not a contract an api should have. `Materials::MAX_SECTION_CHARS` single-sources the bound (shared by attach + write-back via `Materials::SectionValidation`); a boundary test pins exactly-100,000 accepted. A blank section id is likewise refused — quiz sourcing and section markings address sections by it (FR-18 provenance).
5. **`parseFailureReason` added to the attach input** — Phase-1's `RegisterMaterialInput` has no such field (only the parse write-back sets it). Coordinator-pinned on `MaterialType`; validated against the closed vocabulary and refused unless `parseState` is `"failed"` (entities.ts: "Set only while parseState is failed"). The Phase-1 `parseState` derivation is mirrored verbatim: no explicit state → `"parsed"` when sections exist, `"pending"` otherwise.
6. **`setMaterialParseResult` deviations:** unknown ids are NOT_FOUND (Phase-1 no-ops them — "the material may have been deleted while parsing"; delta 2 forbids the silent answer server-side); the payload returns the updated material (Phase-1's write is void) so the client gets the fresh state; `state` is restricted to `parsed|failed` (`Materials::PARSE_RESULT_STATES`) — pending/parsing are attach-time states. Failure keeps the metadata and defaults the reason to `"unknown"`; success clears any previous failure — the Phase-1 semantics verbatim.
7. **Task-create scoping + the one-task-per-material invariant:** `materialId` addresses the owner's materials — unknown, foreign, AND non-uuid ids are uniform NOT_FOUND (Phase-1 throws a client-local `MATERIAL_NOT_FOUND`). A material already linked to a task → VALIDATION_FAILED, where Phase-1 silently re-points `material.taskId` (stranding the earlier task); the ER's unique `materials.task_id` pins one task per material, so the server refuses.
8. **`taskId` on attach can never succeed against a live task** — every task is born with its material (`study_tasks.material_id` NOT NULL; the back-link is created by task creation, exactly Phase-1's `createStudyTask` overwrite). The input is mirrored for shape parity and the conflict is an explicit VALIDATION_FAILED; the flow sets the link via `createTask`.
9. **Attach scope ids are ownership-checked addresses** (delta 2): foreign/unknown/non-uuid `planId`/`taskId` → NOT_FOUND, where Phase-1 trusted the client's ids. `materials(planId:, taskId:)` refuses both-at-once with VALIDATION_FAILED. Reads stay thin resolver bodies — the scoping IS the logic (ticket-01 convention #11) — all through `current_user.materials` / `.study_tasks` / `.study_plans`.
10. **Wire shape notes:** `StudyTaskType.createdAt` is a server row timestamp the TS shape lacks (ticket-01's `KnowledgeNode` precedent); the `node` field is the `getTaskNode` mirror — the task's owned node is otherwise unreachable by id since nodes ride the plan detail tree. `sizeBytes` is a GraphQL Int (32-bit practical ceiling ≈2GB — fine for documents). Phase-1's `blob`/`blobRegistry` inputs have NO wire representation — bytes never reach the api (AD-13; epic-06 owns storage).
