# backend/AGENTS.md — the backend's architecture contract

Rules for everything under `backend/`. Every rule cites its spine decision ID ([`docs/architecture/architecture-synapse/architecture-synapse.md`](../docs/architecture/architecture-synapse/architecture-synapse.md)) — tickets cite this doc; this doc cites the spine.

## What this is

A **Rails 8.1 API-only service** (GraphQL; `.dockerdev/compose.yaml` — postgres 17 + backend so `just up` boots a working api; `schema.graphql` committed as the cross-stack contract; RSpec + RuboCop green). Started as the minimal bootable scaffold (epic-00 T02, one `health` query) and grown since: the AD-12 command core (`ApplicationCommand` + the `System::PingCommand` exemplar — epic P2-1 ticket 01), the AD-13 spine ER (users + the 13 spine entities, user-scoped, uuid PKs — ticket 02) with its test seams (factory_bot factories for every entity + the shared user-scoping RSpec context — ticket 03), the AD-15 auth surface (epic P2-2), and — since epic P2-3 — **the domain operations: 8 command contexts (Plans, Tasks, Materials, Quiz, Flashcards, Chat, Progress, Markings) carrying 28 domain operations on the wire (16 mutations + 12 queries), the Phase-1 repository surface realized server-side** — and, since epic P2-4, **the AD-14 mastery surface is live server-side**: the `Mastery` module (`app/lib/mastery.rb`) is the api's one and only scorer (golden-vector-pinned case-for-case), the mastery score fields ride the wire (`KnowledgeNodeType.masteryScore`/`.state`, `StudyPlanType.masteryScore`, the `streak` query), and freshness decay is live on the wire (the 14-day cap engages wherever the resolvers inject `now: Time.current` — every scoring call site does). And — since epic P2-6 — **the AD-13 byte story is live**: ActiveStorage rides the configured S3 service (`config/storage.yml`: minio in dev/test — the compose R2 stand-in; R2 in production, ENV-only), `createMaterialUpload` presigns a direct PUT (the browser PUTs to the storage provider, never the api; the ActiveStorage direct-uploads REST route is never mounted, guarded by a route spec), and `Material.downloadUrl` mints a short-lived presigned GET per request (never persisted). And — since epic P2-7 — **the job runtime is live**: Solid Queue 1.7 in-process with puma (`SOLID_QUEUE_IN_PUMA`-gated plugin), one named recurring job (the FR-24 due scan). And — since epic P2-5 — **the AD-16 AI surface is live**: the `Ai` context (`app/lib/ai/*` = seam/transport/assembly/prompts/cap/splitter + `app/commands/ai/*` = the AI commands) with the per-user daily cap at the adapter boundary, three generation/grading mutations, and the one non-GraphQL surface — `GET /api/stream` streaming ticket-authenticated SSE with the frozen event contract (ticket 04's `## Comments` — epic P2-8's web client consumes it verbatim). Still deliberately absent: annotations (epic-12). Later backend epics extend this service and own those surfaces; they inherit the conventions below instead of re-deriving them.

## Dev containers only (AD-17/AD-20)

The api runs **only inside its dev containers** — never bare `rails`/`bundle` on the host.

```bash
# Boot the stack (postgres 17 + backend on port 3000) — or: just up
docker compose -f backend/.dockerdev/compose.yaml up -d
# Gates — or: just spec (rubocop first, matching the justfile/CI order)
docker compose -f backend/.dockerdev/compose.yaml run --no-deps --entrypoint "" -e RAILS_ENV=test backend sh -c 'bundle check || bundle install && bundle exec rubocop'
docker compose -f backend/.dockerdev/compose.yaml run -e RAILS_ENV=test -e DATABASE_URL=postgres://postgres:postgres@db:5432/backend_test backend sh -c 'bundle exec rspec'
# Done working on the api? Stack down.
docker compose -f backend/.dockerdev/compose.yaml down
```

**The integration seam (epic P2-3 close-out, 2026-11-04):** `just up` boots the stack, and
`spec/requests/graphql_integration_walk_spec.rb` is the cross-aggregate proof that it stays booted —
one walk executing the Phase-1 happy path (FR-1→FR-20 main line) purely as GraphQL ops, then a second
pass replaying the idempotent client uuids (non-idempotent ops pinned by their typed refusals).
Run just it, without the whole suite:

```bash
docker compose -f backend/.dockerdev/compose.yaml run -e RAILS_ENV=test \
  -e DATABASE_URL=postgres://postgres:postgres@db:5432/backend_test backend \
  sh -c 'bundle exec rspec spec/requests/graphql_integration_walk_spec.rb'
```

New surface should keep the walk green unchanged — it consumes the schema, it never grows with it.

Notes, verified 2026-11-04: the specs are **DB-backed** since epic P2-1 ticket 02 — the spine ER + model specs pin real rows, `spec/rails_helper.rb` sets `use_transactional_fixtures = true` (every example rolls back inside a transaction; `use_active_record` stays at its default — see the comment there for the rspec-rails 8 trap), and every rspec run therefore needs postgres: the compose `run` (no `--no-deps`) starts the db service, and the dev entrypoint bundle-installs and runs `db:prepare` before handing off. **Override `DATABASE_URL` to a test database** (`postgres://postgres:postgres@db:5432/backend_test`) on every rspec run — without it the entrypoint's `db:prepare` would prepare the development database instead, and the spec run would sit on it. RuboCop stays DB-free (`run --no-deps --entrypoint ""` + bundle guard). CI mirrors this with a `postgres:17-alpine` service container + `DATABASE_URL` + a **`db:create db:migrate`** step before rspec — deliberately **not** `db:prepare`: on a freshly created (or empty) database `db:prepare` auto-runs `db:seed` (Rails behavior), and CI's service container presents exactly that state on every run, which would commit the demo account before the suite. The local dev entrypoint keeps `db:prepare`: the persistent volume means it normally migrates an existing database instead of creating one (and the demo-seed specs are seed-state-agnostic regardless). **`RAILS_ENV=test` is required for rspec** — the service env defaults to `development` and request specs then 403 on HostAuthorization (development-only middleware). Grep-level truth over stale claims: re-verify commands against this file's `compose.yaml` when touching tooling.

## GraphQL is the only web-facing surface (AD-12)

- One surface: `POST /graphql` → `GraphqlController#execute` (`config/routes.rb`). The AD-16 SSE endpoint (`/api/stream`) is the **only** sanctioned future non-GraphQL surface; presigned storage URLs (AD-13 — landed, epic P2-6) point at the storage provider (minio dev / R2 prod), never at the backend.
- Depth/complexity limits + Dataloader batching stay on: `ApiSchema` mounts `GraphQL::Dataloader`, `max_query_string_tokens(5000)`, `validate_max_errors(100)`.
- **No Relay/node identification**: the install generator's node/connection scaffolding was removed; ids are plain UUID strings (below). Add Relay-style connections only when a list actually paginates.

## Command-layer-first (AD-12)

- Every use case is an **`ApplicationCommand`** class (dry-initializer + dry-monads `Result`): resolvers/mutations **parse args → authorize → call the command → map the Result**; jobs are thin wrappers that load a record and call a command.
- **Sanctioned reads carve-out** (the ticket-01/02 deviations the epic P2-3 review confirmed as the convention): bare reads — lists, by-id details, the 1:1 hub reads — resolve directly through the current user's scoped association paths in thin resolver bodies; no command wraps a plain SELECT, because **the scoping IS the logic**. Anything with a decision in it (writes, cascades, sweeps, cross-graph checks, upserts) is a command.
- **Business logic never raises** — failures are `Failure` values. Exceptions are for infrastructure faults, not domain outcomes.
- The core landed 2026-11-04 (epic P2-1 ticket 01): `app/commands/application_command.rb`. `Context::VerbNounCommand` subclasses declare dry-initializer `option`s, override the `#authorize` hook when needed (default allow; deny with `Failure(:UNAUTHORIZED, …)`), and implement `#call` returning a Result. `.call(**args)` wires authorize → call and **never raises**: an unexpected `StandardError` becomes a typed `Failure(:INTERNAL, context: { message: "unexpected <Class>: <msg>" })`. The deliberate exceptions (misuse fails fast at the seam instead of masquerading as a domain outcome): the `Failure(code, context)` factory raises `ApplicationErrors::InvalidCodeError` (an `ArgumentError`) for a code outside the closed enum, and construction misuse — an exception from `new(**args)` itself, e.g. a raising dry-initializer `default:` proc — propagates out of `.call` (the instance is built before the rescue region; only authorize/call are wrapped). `System::PingCommand` (`app/commands/system/`) is the pattern exemplar; its spec is the template for direct command testing (AD-10). Do not introduce a second service-object style next to it.
- The **delta-3 idempotency triad** (same-user client-uuid replay → `Success` with the original rows untouched · the uuid owned by a different user → `VALIDATION_FAILED` · a non-uuid → shape refusal) is hand-copied across the 5 idempotent create commands (Plans/Tasks/Materials/Quiz/Flashcards) with identical semantics — each cites delta 3 + FR-4. Extract a shared concern when the **sixth** arrives (annotations, epic-12), not before.

## Closed error enum ↔ web `AppError.code` 1:1 (AD-12 + AD-9)

- GraphQL error `extensions.code` is a **closed enum**, defined once in `backend/` as `ApplicationErrors::CODES` (`app/commands/application_errors.rb`; frozen symbols, this exact order):
  `UNAUTHORIZED | FORBIDDEN | NOT_FOUND | VALIDATION_FAILED | RATE_LIMITED | CAP_REACHED | INTERNAL`
- `ErrorPresenter` (`app/graphql/error_presenter.rb`) maps an unwrapped command failure (`result.failure`, an `ApplicationErrors::Failure` — `code` symbol + free-form `context` hash) into the error payload `{ message:, extensions: { code: "<CODE>" } }`; resolvers/mutations feed that to `GraphQL::ExecutionError.new(payload[:message], extensions: payload[:extensions])`. `message` comes from `context[:message]` (an English log line, AD-9) and falls back to the code string; the rest of the context is never copied into the payload.
- Frontend mirrors it as `AppError.code` (`frontend/src/data/errors.ts`), mapping **1:1 via `extensions.code`**. **Adding a code touches both sides in the same change** (AD-17's one-contract rule applied to errors).
- The api is **not user-facing** — its strings are error codes and English log lines, never rendered verbatim (AD-9). The web maps codes to `t()` keys and shows bilingual toasts; it never renders server strings.

## Ids: plain UUID strings (AD-12 / AD-15)

- Primary keys are **uuid columns; ids travel as plain UUID strings** — **no GlobalID**, no integer leakage.
- **Clients may supply ids on create** — this is what makes the first-login import idempotent (AD-15): whole-document upload, one transaction, one mutation; same-user id conflicts skip (retry-safe), an id owned by a *different* user is `VALIDATION_FAILED` with ownership verification (never silently link to another user's rows, FR-4).
- Every user-owned row is scoped by `user_id`, enforced in the command layer and asserted by a shared RSpec context (AD-13). The single sanctioned exception: the Square's public-plan read path — **structure only**, never Materials/Annotations/Mastery Scores (NFR-7).

## Pagination: plain lists until a list truly paginates (AD-12)

- Return plain lists by default. Relay connections are added only when a list actually paginates — the first candidate is evidence history. Don't preempt.

## The contract: `backend/schema.graphql` (AD-17 / AD-18)

- `backend/schema.graphql` is **the only cross-stack artifact** — committed, IDL-only, dumped with `bin/rails graphql:schema:dump` (inside the api container; the custom rake task in `lib/tasks/graphql.rake`). The dump is **idempotent**: `spec/graphql/schema_dump_spec.rb` re-dumps twice and asserts byte-identity with the committed file — keep it green.
- **A contract change touches both stacks in the same change**: api mutation/resolver + `schema.graphql` dump + web codegen regeneration land together (AD-17's no-shared-package rule; web consumes the schema via graphql-codegen).
- IDL-only is deliberate: graphql-ruby 2.5's introspection-JSON dump is broken against the json gem 3.x bundled with Ruby 3.4 (quirks_mode), and the web contract only needs the IDL.

## AI executes server-side only (AD-16 — landed, epic P2-5)

- Provider keys live **only in api config** (ENV + `.env.example` — reference pattern; `PROVIDER_KEY` is boot-fail-fast in production). The provider sits behind the **`Ai::Provider` seam** (`app/lib/ai/provider.rb`) over the OpenAI-compatible `Ai::GlmClient` (stdlib Net::HTTP — no HTTP-client gem; GLM first, OQ-4, base URL/model/key/timeout all ENV-config) — **a provider swap is config, not code**. The seam maps every transport fault to `Failure(:INTERNAL)` and enforces the cap before any HTTP leaves the process; specs override `.adapter`, never the transport.
- Context assembly lives in `Ai::ContextAssembler` (Postgres-sourced only, deterministic whole-section bounding under `AI_CONTEXT_BUDGET_TOKENS` ≈ 8k — the assembled estimate never exceeds the budget, headers/padding budgeted, ` …[truncated]` marker + `truncated` flag on any cut). Prompts live in `Ai::Prompts`; reply-JSON extraction in `Ai::ResponseParser` (string-aware balanced scan); the proposal tag contract in `Ai::TaggedReplySplitter` (`<outline>…</outline>` streams as tokens, `<proposal>…</proposal>` parses for the terminal — the JSON never rides the token wire).
- The AI commands (`app/commands/ai/`) wrap the seam and persist through the epic P2-3 commands (the only write paths): `generateQuiz` (replay-before-spend — an owned client_uuid returns the session without a provider call; normalization is the enum-guard: only open/choice shapes with in-scope addresses survive, zero survivors → INTERNAL), `generateFlashcards` (one card per usable section, server-minted card uuids), `gradeOpenAnswer` (pure computation — outcome/rationale/server-built citation; the client's `recordEvidence` makes evidence). Model-reply JSON keys are camelCase (`correctOptionIndex`).
- All AI operations are GraphQL mutations **except token streams**: `GET /api/stream` (`Api::StreamController`) emits them, authenticated by single-use stream tickets alone. **The ticket contract + event vocabulary are FROZEN in `.scratch/phase-2/epic-05-ai-server/issues/04-sse-ticket-stream.md` `## Comments` — epic-08's web client consumes it verbatim.** Shape: `createStreamTicket` mints the secret (op + language + grounding inputs INSIDE the payload jsonb — query params carry only `ticket` + `op`); the endpoint 401s bad/expired/replayed/op-mismatched tickets and never retries; events run `rung` (request-derived posture — escalated → "answer", else "hint") → `token`* → `citation` (companion only) → `terminal{code}` (closed enum; "OK" on success; proposals add the confirmProposal-ready payload). Live tickets per user are bounded at mint (`MAX_LIVE_TICKETS` → RATE_LIMITED — the daily cap counts redeems, not mints).
- Cost cap (FR-34): 50 AI calls/user/day (`AI_DAILY_CALL_CAP`) + the ~8k context-in bound, enforced at the adapter boundary (`Ai::DailyCap` — atomic `INSERT … ON CONFLICT … RETURNING`, midnight-UTC `ai_usage_counters` row per user-day, every call counted including stream restarts).
- Generation is in-request (streamed) — **no AI jobs**. CORS: rack-cors allowlists `/graphql` + `/api/stream` from `CORS_ORIGIN` (comma-separated; blank = no cross-origin — the safe pre-cutover default; epic P2-8 sets it). One manual live probe per provider-config change: `bin/rails ai:probe` (S6 pattern, owner-gated on OQ-4 terms verification — never in CI).

## Jobs: Solid Queue in-process (AD-19 + A9 — landed, epic P2-7 ticket 01)

- **Solid Queue 1.7** (`~> 1.7.2`) runs **in-process with puma** via the gem's puma plugin, gated on `SOLID_QUEUE_IN_PUMA` (config/puma.rb) — no separate worker service; compose dev sets the env, production boots puma with it set. Test env keeps the `:test` adapter (development.rb/production.rb set `:solid_queue`) so the supervisor never boots under rspec — jobs are tested directly.
- The queue tables live in the **SAME Postgres via `DATABASE_URL`** (installer's separate-queue-database shape deliberately not used — no `connects_to`; the schema landed as migrations 20261104120000–02). **Production must point `DATABASE_URL` at Neon's direct (non-pooled) connection URL** — the polling dislikes transaction-mode pooling (deploy checklist).
- Recurring v1: **exactly one named job** — the FR-24 re-queue due scan (`config/recurring.yml` → `Requeue::ScanJob`, every 10 minutes; polling-while-awake cost is negligible; the upstream finished-jobs cleanup default was dropped as unnamed work). Correct-on-wake: due-ness is recomputed from source timestamps on every wake, never accumulated while asleep.
- **No keep-alive loop** — cold starts are accepted per AD-20; keeping the service awake would drain Neon's free compute hours. Guarded lexically by `spec/config/no_keep_alive_spec.rb` (spin-loop shapes in app/config/lib fail the suite). No new background work without a named need.

## Data model & migrations (AD-13)

- ActiveRecord entities follow the spine ER, one model per entity, **no renames** at the entity-ownership cutover (AD-14 moves mastery computation to Ruby then; its rules are ADR-0001 verbatim, verified by golden vectors from the TS suite). **`Mastery` (`app/lib/mastery.rb`) is the api's ONLY mastery/score implementation** (epic P2-4 ticket 02) — node scores, states, rollups, and the streak are computed nowhere else until the AD-14 cutover retires the TS side; it is pinned case-for-case by the golden vectors (`spec/fixtures/mastery_vectors.json`, exact-equality — `spec/lib/mastery_spec.rb`). **The ER landed 2026-11-04** (epic P2-1 ticket 02): users + 13 spine entities — uuid PKs (`gen_random_uuid()` server default, client-suppliable on create), `user_id` FK (indexed) on every user-owned row, enum-ish strings pinned by model `enum` + DB check constraints, field-level decisions in the ticket's `## Comments` (`.scratch/phase-2/epic-01-api-foundation/issues/02-er-migrations.md`).
- **User scoping has a standing test (AD-13 / FR-4) — one include away, or zero:** the shared examples `"user-scoped"` live in `spec/support/user_scoping.rb`, and `spec/models/user_scoping_spec.rb` is the roster keeper. It discovers every concrete model dynamically (`ApplicationRecord.descendants` after an eager load — the test env is lazy outside CI) and proves per model: the `User` has_many lists **only** the owner's rows, `find_by(id:)` on another user's row → nil, `.find(id:)` → `ActiveRecord::RecordNotFound`, and a same-user read succeeds. **Landing a new model needs no spec edit:** give it `belongs_to :user` + a `user_id` column + a `User` has_many named `model.name.underscore.pluralize` (the roster spec fails with an actionable message for any of the three), and a factory named after the model (`model.name.underscore`) — the roster picks it up. Model specs may also include it directly: `include_examples "user-scoped", described_class` (a second arg overrides the has_many name).
- **Factory rules (AD-10/AD-12):** factories live in `spec/factories/` (one file per entity, table-style plural filenames — landed 2026-11-04, epic P2-1 ticket 03). **Never pre-assign uuid ids** — the `gen_random_uuid()` server default fills them; a client-supplied id is an explicit test choice, not a factory default. Sequences only for uniqueness-bearing fields (`users.email`). Multi-association factories pass `user:` down so the whole graph shares one owner (`association :material, user: user`); the task↔node triangle does the insert dance from ticket 02's Comments (node/material with `task_id` null → create the task → back-fill `task_id` in `after(:create)`). **Overriding an association (`material:`/`node:`/`question:`/…) with a record of another user requires the consistent `user:` overrides across the whole graph** — a cross-owner triangle silently breaks the AD-13 model; the default-factory-graph guard spec (`spec/models/study_task_factory_spec.rb`) pins the single-owner invariant for the triangle. (Factory-definition files live only in `spec/factories/` — factory_bot_rails loads every `.rb` under it at boot, so specs must never live there.)
- **strong_migrations is on** (`config/initializers/strong_migrations.rb`); plain schema migrations — no data-migration split, no logidze, no soft delete.
- **Material files** go to object storage via ActiveStorage → **Cloudflare R2** (Render disk is ephemeral) — **landed 2026-11-04, epic P2-6**: original bytes to the configured S3 service (minio dev/test, R2 prod), extracted sections/text to Postgres, parsing stays client-side (AD-7). Uploads presign via `createMaterialUpload` (`Storage::CreateMaterialUploadCommand` mints the Blob server-side — key convention `materials/{user_id}/{uuid}{ext}` from the VALIDATED content type — attaches it to `Material.original`, and returns a v4 presigned PUT (15-min TTL, signed over the declared content type); the browser PUTs directly to the provider; the ActiveStorage direct-uploads REST route is never mounted — `config.active_storage.draw_routes = false` + `spec/routes/active_storage_route_guard_spec.rb`). Downloads are short-lived presigned GETs minted per request by the `Material.downloadUrl` field (5-min TTL, never persisted). minio lives in the dev compose (loopback-published :9000, one-shot bucket init) as the R2 stand-in; the four `R2_*` ENV vars are the production contract (`.env.example`), provisioned by ticket 03 (owner-side).

## Config: ENV only (AD-12 / AD-20)

- `DATABASE_URL`, `JWT_SECRET`, `LOGIN_RATE_LIMIT_THRESHOLD`/`LOGIN_RATE_LIMIT_WINDOW_SECONDS` (epic P2-2 ticket 02), `DEMO_EMAIL`/`DEMO_PASSWORD` (epic P2-2 ticket 03), `PROVIDER_KEY`/`PROVIDER_BASE_URL`/`PROVIDER_MODEL`/`PROVIDER_TIMEOUT_SECONDS` + `AI_DAILY_CALL_CAP`/`AI_CONTEXT_BUDGET_TOKENS`/`AI_STREAM_TICKET_TTL_SECONDS`/`CORS_ORIGIN` (epic P2-5), `R2_*` — documented in `backend/.env.example`; the dev compose sets what the scaffold needs today (`DATABASE_URL`, `RAILS_ENV`, and `JWT_SECRET` as a fixed dev-only default since epic P2-2 ticket 01, plus `DEMO_EMAIL`/`DEMO_PASSWORD` at the documented dev defaults since ticket 03). ## Naming conventions (spine Consistency Conventions)

- Commands: `Context::VerbNounCommand` (e.g. `Plans::CreatePlanCommand`), one directory per context under `app/commands/`.
- Types/files PascalCase; GraphQL fields camelCase; entities/files match the ER names verbatim (no renames at cutover, AD-13/14).
- Specs colocated in `backend/spec/`, `type:` metadata per rspec-rails; factories in `spec/factories/` and the shared user-scoping context in place (epic P2-1 ticket 03 — see "Data model & migrations" for the factory rules and the context's usage contract).
